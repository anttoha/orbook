Прочитай `CLAUDE.md` и `docs/specs/<часть>/spec.md`. Если в spec есть открытый вопрос — перечисли и остановись.

1. **План в 3–8 шагов** — покажи коротко (какие файлы, в каком порядке). Бэкенд-изменения идут первыми.
2. **Бэкенд (если spec требует) — только в репозитории `/opt/orbook-be` и по его правилам:** сначала прочитай `/opt/orbook-be/CLAUDE.md` и `docs/BETRIEB.md`; покажи пользователю план и жди «ок» (так требуют правила бэкенда); код + тесты, `make lint test`; сразу обнови `docs/API.md`, `docs/FRONTEND.md`, `docs/openapi.json`; маленькие коммиты там; миграции с бэкапом; выкладка только через `/opt/orbook-be/scripts/update.sh`. Не трогай чужие сервисы сервера. Фронт этой части начинай после того, как бэкенд выложен и проверен (`curl` по `/api/health` и новому эндпоинту). Существующий тест не меняй, чтобы он прошёл: странный тест — вопрос пользователю.
3. **Фронт:** по дизайну, пиксель в пиксель насколько возможно. Только токены и компоненты из `src/ui/`. Новый общий компонент — в `src/ui/`, не копируй разметку.
4. **После каждого шага:** `npm run lint` и тесты затронутых файлов, коммит, и пользователю 2–4 строки по-русски: что сделал, в каких файлах, **почему так** (это главное — пользователь учится).
5. **Ревью перед концом:**
   - каждый `useEffect` действительно нужен (не производное состояние, не копия пропсов, есть очистка);
   - нет глубокой вложенности — длинные функции разбиты на маленькие с понятными именами;
   - все поля, которые могут быть `null`, обработаны;
   - нет секретов, `console.log`, мёртвого кода;
   - тексты интерфейса — немецкие и как в дизайне.
6. Затем запусти `/orb-check <часть>`.
